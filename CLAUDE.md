# Marqoom — project guide

Marqoom (مرقوم) documents ongoing Quranic data standards work: shared concepts, names, data formats and rules that reduce repeated integration decisions. Two standards are published: Quranic terminology and Quranic audio data. Text, and the formats of segmentation and timing, are future areas, not specifications to invent from the strategy.

The code lives in the public [marqoom-specs](https://github.com/marqoom-specs) GitHub organization, as [marqoom-specs/specs](https://github.com/marqoom-specs/specs) (code MIT, standards text and data CC BY 4.0, see `README.md`); the lint tool is [marqoom-specs/quranic-terminology-lint](https://github.com/marqoom-specs/quranic-terminology-lint). The org avatar is `design/logo/github/avatar.png`, the Monolith mark on the light page background.

Ratq (رتق) helps developers discover tools and datasets, including their licenses, versions and access details. Resources can remain in their own repositories; Marqoom documents standards and links their implementations.

Marqoom calls its work **standards** (معايير), in titles, navigation and its own prose. The terminology standard is published as **v0.1** (`terminologyVersion` in `lib/versions.ts`): every terms page shows it as the badge under its title, in place of the source's "draft", and the overview's Terminology card shows the same value. Each dictionary entry's table shows it too, as «الإصدار» / Version in place of the source's `draft` status (`ENTRY_STATUS` in `scripts/import-terminology.py`, which reads the same constant and stops if an entry ever has another status). Imported source texts keep their own wording, including "specification". The audio standard is published as **v0.1** too (`audioVersion`), with the same badge on its pages and its card.

## Source authority

The user's requested source is [Quran.ws PR #9](https://github.com/quran-ws/docs/pull/9), final revision `9bf0db1bac9a8186bced687950e0ccf04311d3e3`. Its complete original tree is archived in `public/sources/quran-ws-pr-9.tar.gz`. It supersedes the older vocabulary-sheet summaries previously published here.

- Preserve the source's definitions, examples, conditions, evidence and review statuses in both languages.
- The decision record is not published: the importer skips it, drops the standard's three pointers to it (`EDITS` in `scripts/import-terminology.py`, which also drops the upstream build instructions from the registries and the dictionary's contributing section, drops the dictionary's opening note, and calls a dictionary category «موضوع» rather than «مجال» in Arabic), and `/docs/terms/decisions` redirects to the standard.
- The separate developer naming guide (`naming.md` in the source) is not published either; the standard is the only naming page, and `/docs/terms/naming` redirects to it.
- Do not silently correct source inconsistencies or infer adoption from publication. The standard's pages and entries show its version (v0.1) in place of the source's draft status.
- Imported `.md` files under `content/docs/{ar/,}terms/` are generated by `scripts/import-terminology.py`. Change the upstream source and pinned archive deliberately rather than editing generated prose.
- Terms changed after expert review are listed in `scripts/term-changes.json`, keyed by the source's code, each with its date and reason. `rows` rewords one field of an entry in place (so far the sukun's shape, «رَأْس حَاء»). A rename also carries its former names and a bilingual note, and both import scripts apply it: the entry takes its new code, display and Arabic names and moves to its alphabetical place, every link and sorted list follows, the index row moves, the old code is shown as a deprecated name with the note (rules 046, 047) and its old anchor still reaches the entry, and the concept map keeps the old code as a recorded spelling. Source names (the dabt name, shape and mushaf-introduction wording) stay as they are (rule 040). So far `omitted_alif` became `dagger_alif`, «الألف الخنجرية», and rule 005's example follows it (`EDITS`). A rename without a new `code` changes the Arabic name only, keeping the code and English name (rule 037): every plain use of the old name follows (source names are vocalized, so they don't match), `wording` fixes any Arabic sentence the new name changes, and the entry gains a dated note. So far `small_yaa` became «الياء الفارسية» (its note says it is not U+06CC FARSI YEH) and `letter_relation` became «التجاور». The [lint tool](https://github.com/marqoom-specs/quranic-terminology-lint)'s `concepts.tsv` must follow every rename.
- Short codes are Marqoom's own addition, in `scripts/short-codes.json`, keyed by registry and then by the entry's code, with the date, the reason and a bilingual note. The importer gives that registry's table a `short_code` column beside `alternative_spellings` and puts the note above it; it stops if a short code is used twice or is already a code or a spelling in the table. The standard's "Clear names" section gains one paragraph (`SHORT_CODE_RULE` in `scripts/import-terminology.py`): a recorded short code may stand for an entry's code where a name has to stay short, such as a file name, and both forms are valid there. So far the 20 riwayahs have one (`As-Hf` for `hafs_an_asim`) and so do the five rows of the `wajh` registry (`qsr` for `qasr_al_munfasil`), the codes recitation file names use. Qiraat and rawis have none, because the file names' `Kh` would name both `khalaf` and `khalaf_al_ashir`. The [lint tool](https://github.com/marqoom-specs/quranic-terminology-lint) does not read short codes yet.
- Registries Marqoom adds are in `scripts/registries/*.tsv`, written in the source's own shape: `#` lines are commentary, the first one the title (English, then ` — `, then the Arabic title) and the last one the tab-separated header, which starts with `code` and ends with `ref`. The commentary says why each row is there and what its `ref` cites; it is not published. The importer renders each one the way the source renders its registries, in its alphabetical place on both registries pages, and stops if a row is incomplete, a code is used twice, or a column listed in `REFERENCES` points at a code the registry lacks. The term a registry lists names it in `scripts/term-changes.json` (`registry`, with a dated bilingual note): the entry gains its Registry row above its other spellings, and the note. So far there is one, `wajh`: the four wajhs recitations name in their labels (qasr and tawassut of the madd munfasil, silah and sukun of mim al-jam) and the label `jama`, which `kind` marks as not a wajh. `excludes` names the other wajh of the same place. Codes are derived from the vocalized Arabic by the source's `tools/translit.py` and checked with its `tools/check_registries.py` (both in the pinned archive); every row cites al-Nashr by volume and page. `scripts/check-site.py` counts the registries (8). The [lint tool](https://github.com/marqoom-specs/quranic-terminology-lint) does not know this registry yet.
- The terms are Marqoom's own standards: derived from that source, but independent. The site does not name Quran.ws or the PR as their origin: no source link or attribution page on terms pages, and no "imported" wording in Marqoom's prose. The old Sources page URL redirects to the terms overview. The archive and its license notice stay in `public/sources/` for the import scripts. Quran.ws still appears as one of the projects on the overview, and links inside the imported text are left as they are.
- The separate [Quranic terminology lint](https://github.com/marqoom-specs/quranic-terminology-lint) tool is documented from v0.5.0 at `8eac1ef24e83688af808ec29cc8d6f2b03d48c62`. It has two checks, each with its own hook and command: `quranic-data` for the data a project stores and publishes (read against the registries), and `quranic-terminology` for names in code. The terms overview's "How do I use them" section (`#use`) leads with installing it as a pre-commit hook and repeats its `.pre-commit-config.yaml` and an example finding; update that section with the tool page when the documented release changes. The tool page itself (`content/docs/{ar/,}tools/quranic-terminology-lint.mdx`) is a short guide in the user's voice, modelled on their post about the tool, not a copy of the README: a data export (`exports/al-baqarah.json`, Warsh numbering with no riwayah stated) and one `example.py` walked through, question headings for set up, exceptions and the unsafe fix, and a link to the README at the release tag for everything else (the full rule table, CLI and CI, every config key). Its examples are real output from that release; rerun the tool when the release changes. It shows no source link under the title. It ends with `ToolCta` (`components/tool-cta.tsx`): "Try it in your project", whose main button copies the `.pre-commit-config.yaml` setup (both hooks) and whose second opens a new issue on the tool's repository; keep its `rev` on the documented release. Do not confuse its pre-commit hooks with the terminology skill packaged in the PR.
- Never apply automatic terminology replacement to source quotations or imported specifications. Their noncanonical names may be intentional examples or evidence.

## The audio standard

The Quranic audio data standard (`content/docs/{ar/,}audio/`) is a content model: what must be known about a reciter, a recitation, an audio file and a timing, each piece of information with a level (required, expected, optional). It decides no ids, field names or formats except the reciter code and the file fingerprint. Its text is the user's own, drafted in Notion ([Quranic audio data standard](https://app.notion.com/p/41ba75df6ece80fd8eceed8f0d0fa46c)); the English pages carry that wording as it is, and the Arabic pages translate it.

- Four hand-written MDX pages per language: `index` (the problem, what the standard defines, the levels, the four models), `models` (the four models, each with its table and a JSON example), `file-names` (the file name and the tags) and `registries` (the reciter registry and the file name codes). The Notion draft is one page; here its sections became pages, its toggles became open text, and the file name section took four headings. Change the wording in both languages together, and keep every heading's `[#anchor]` the same in both.
- Arabic names every term by the dictionary: «تسجيل التلاوة» for a recitation («التسجيل» once it is clear), «نمط الأداء» for style, «مرتبة القراءة» for pace, «مفتاح الآية», «نظام عد الآي». The levels are «مطلوب», «متوقع», «اختياري». Prose numbers are Arabic-Indic; codes, file names and JSON stay as they are.
- Write the rules of the file name as Marqoom's own, with no source named for them. The page lists no producer codes and has no producer registry.
- `scripts/build-audio.py` (also run by `npm run check:content` with `--check`) writes the reciter registry from `scripts/audio/reciters.tsv` between the `reciters:start` and `reciters:end` markers of both registries pages, and reads the models back from the pages into `lib/audio-data.json`: each model's table (label and level), its question from the overview, whether each piece is known in the JSON example (`MODELS` maps a piece to the example's keys; null means unknown), and the timing entries. It stops if the two languages disagree, if a file name code differs from `scripts/short-codes.json`, if an example cites a reciter the registry lacks, or if the home page does not quote the number of reciters. Run it after changing a table, an example or the registry.
- The file name codes are the terminology registries' own short codes (`qiraat` and `wajh`, see Source authority); the audio registries page lists them with `-` in place of `_`, and the terminology notes link back to the file name page.
- `lib/rehype-reading.mjs` dresses the audio tables without changing the text: a cell that is only a level word becomes a `.level` tag, an Arabic name on an English page is marked `lang="ar"`, and a table over 30 rows (the reciter registry) gets the reference viewport.
- The figures are in `components/audio-figures.tsx`, drawn from `lib/audio-data.json` so they say nothing the pages do not. `ModelsFigure` (overview) draws one real reciter's three recitations with a column for each model, and lists the chosen model's pieces of information by level, marked known or unknown in the example; below 38rem of its own width it becomes an outline. `TimingFigure` (models) places the example's seven ayah timings on the file by their own start and end, left to right in both languages, beside seven ayah files. `FileNameFigure` (file names) marks the fields of the example name by model. `RegistryFilter` is a search field over the reciter table, which stays whole in the page; it folds Arabic letter forms, case, spaces and hyphens. Their styles are in `reading.css`. The facts only the first figure states (the three recitations and their file counts) are in the component.
- `scripts/check-site.py` checks the four models, the registries' headings and their row count, and that the site search finds a reciter in both languages.

## Structure and presentation

- `content/docs/index.mdx`: Marqoom overview. `terms/`: terminology layer; `audio/`: the audio standard; `tools/`: implementation tooling. `ar/` mirrors the English paths. `meta.json` controls navigation.
- English `/docs`, Arabic `/ar/docs`; Fumadocs directory-based locale parsing with hidden default locale.
- `app/[lang]/layout.tsx` sets the server-rendered `lang`/`dir`, Thmanyah Sans fonts and translated UI strings. Keep both scripts in the sans typeface.
- The Monolith brand mark is `public/brand/monolith.png`, used in navigation with Next Image. `app/icon.png` is its 64px favicon. Keep its asymmetric crown, connected feet, and orientation in Arabic. The hero has no logo image. Design references and the flat alternative are in `design/logo/monolith/`.
- The site lives at https://marqoom-specs.com (`siteUrl` in `lib/site.ts`, a custom domain in `wrangler.jsonc`). It is the site's only address. `app/robots.ts` and `app/sitemap.ts` are built on `siteUrl`.
- Link previews: every page has Open Graph and X tags (`generateMetadata` in `app/[lang]/docs/[[...slug]]/page.tsx`, `metadataBase` in `app/[lang]/layout.tsx`) with one image per language, `public/og/{ar,en}.jpeg`. `scripts/build-og-images.py` draws them with Chromium from the hero's own shader, the Monolith mark, the fonts and `terminologyVersion`: the title with only the version pill under it. Rerun it when any of those change.
- `components/toggles.tsx` provides locale/theme controls. Language switching prefetches the canonical counterpart, retains the query and visible stable heading, and avoids an extra `/en` redirect.
- `app/globals.css` controls readable light/dark surfaces, restrained navigation blur and reduced-motion-aware micro animations. Keep body text crisp, tables scrollable and code identifiers LTR in Arabic. `--marqoom-gold` carries the figures' gold into the rest of the page (the areas-of-work statuses, with a pill on the published ones); it is a shade deeper in light so small text keeps its contrast. The areas of work are layers, each a rounded card of its own: dashed for a planned standard, solid and hatched for a published one.
- `components/marqoom-hero.tsx` renders the overview hero, the only shader on the site: flowing strands (recited text) in the ink-and-gold palette. `hero-webgl.tsx` draws it with a hand-written WebGL2 shader and no library, because Firefox-based browsers on Linux have no WebGPU. Keep the CSS fallback, the reduced-motion still frame and the RTL mirroring. The hero uses the `silk` treatment (the bare flow). `halftone` (the flow as printed dots) is kept as a ready alternative: pass `variant="halftone"` to `MarqoomHero` in `app/[lang]/docs/[[...slug]]/page.tsx` to switch. Keep both working. Headless Zen can capture the hero for checks.
- `.claude/skills/shaders` is the agent skill for the shaders.com WebGPU library, which was tried first for the hero and dropped. The site does not depend on that library; the skill is kept for experiments only.
- Every shape a figure fills or outlines is rounded, as the site's cards and pills are: tiles, chips, bars, a highlighted line, the part of a bar being read. No square blocks, no flat highlight bands, no underline standing in for a chip. The user has asked for this more than once; check a new figure in dark mode, where a square block shows most.
- `app/[lang]/visual-lab` keeps the four full figure explorations (`components/visual-lab/`): spellings, the concept map, ayah counts and the qiraat ring. The terms overview carries the concept map; the dictionary page does not. Qiraat and its registry use the full transmission ring. Preserve their simple hover/link interaction, and keep them usable by touch: on a touch screen the map's first tap selects a concept and a second tap on it opens the entry, and the map keeps the selected concept in view when it scrolls sideways. Check phones (360–390px) after changing a figure. The terms overview (`content/docs/{ar/,}terms/index.mdx`) is built around all four full, interactive figures (`SpellingsFigure`, `DictionaryExample`, `CountsFigure`, `TransmissionExample` in `components/doc-examples.tsx`) so it explains the whole terminology idea visually; elsewhere spellings and counts use small, passive `inline` variants. Arabic figure numbers use Arabic-Indic digits (`ar-u-nu-arab`). In Arabic a dictionary category is a «موضوع» (topic), never a «مجال»; «مجال» keeps its other senses (areas of work, a concept's domain). Captions and map definitions are bilingual. The concept map has one search field, which matches codes, display names, Arabic and recorded spellings, lights the matches on the map and links to their entries. Do not add other forms or pickers to these figures. They read `lib/visual-lab-data.json`, which `scripts/build-visual-lab-data.py` regenerates from the pinned archive (requires PyYAML).
- The overview's project cards are followed by `JoinCta` (`components/join-cta.tsx`): a dashed "Working on a Quran project?" band with the three projects' logos (`public/projects/logos/`, sources in `public/projects/SOURCES.txt`) and an empty seat, whose main button, "Tell us about your project", opens the visitor questions (`SurveyButton`); the second links to `terms#use`. That section, "Why a shared standard", makes the case in two figures (`components/doc-examples.tsx`). `NetworkFigure` draws an adapter between every two projects (n(n−1)/2) against at most one per project through the standard (n); it grows from two to the four projects on the page as it comes into view, and "Add a project" goes up to twelve. Its caption says this is the worst case. `IntegrationFigure` then diffs one ayah record against the standard's names, after the prose's second reason: some mismatches give wrong data rather than errors. Every name and note in it is taken from the dictionary, registries and naming standard. Its caption states that only names are settled so far; keep that limit if the figure changes.
- Pages of a standard (terms and audio) have a Suggest edits toggle beside the version badge (`components/suggest-edit.tsx`, styles in `reading.css`). Once on (remembered in `localStorage`), one chip follows the block under the pointer and opens `.github/ISSUE_TEMPLATE/edit.yml` on Marqoom's own public repository (`repoUrl` in `lib/site.ts`), filled with the page URL and heading, the file under `content/docs/`, the concept on dictionary pages, and the quoted text. It never points at the source's repository and names no source.
- `app/[lang]/visual-lab/navigation` compares ways into the dictionary (`components/visual-lab/dictionary-nav.tsx`): term finder, category shelf, families outline and a category term strip. They are mockups; the chosen direction is the category cards on the dictionary page, with the concept map kept on the terms overview.
- The dictionary page is the way into the dictionary: it opens with "Browse by category" (`#categories`, `components/dictionary-categories.tsx`), one card per category in the dictionary's order with its term count and its best-connected terms, each opening the category page. A full index of all 180 terms was tried and rejected as too dense, and the concept map was removed from this page; the site search finds a single term. The sidebar lists the dictionary as one link (`oneDictionaryLink` in `app/[lang]/docs/layout.tsx`), not its 19 category pages, so `page.tsx` gives those pages a Terms › Dictionary breadcrumb and their previous and next pages from the full tree.
- `lib/rehype-reading.mjs` changes presentation without changing the imported files or search content: dictionary definitions and purposes come before compact metadata; long tables have a keyboard-scrollable viewport. The standard opens with "The rules at a glance" (`#rules`), a table built from each section and rule heading and the rule's first sentence, so it follows the rules when they change; its heading is the standard's first TOC entry. Keep all reference text in the continuous reading flow and preserve every heading anchor.
- `components/visitor-survey.tsx` asks visitors three questions (`lib/visitor-survey.ts`: who they are, which data they work with, whether they would use the standards), mounted once in `app/[lang]/layout.tsx` with styles in `app/[lang]/visitor-survey.css`. It opens after 8 seconds on the site (counted across pages while the tab is visible), never while search, the mobile menu or a text field is in use, once per visitor; a dismissal holds for 30 days (`localStorage`). Phones get a modal bottom sheet (swipe the handle, tap outside or Esc to close); wider screens get a non-modal card in the inline-end corner that does not take focus unless the reader opened it. Dismissed without answering, it becomes a pill in the same corner for the rest of the visit (`sessionStorage`), showing how far the reader got; reaching the last step counts as answering, so a finished set never becomes a pill; the pill reopens it where they stopped and its × hides it. `SurveyButton` opens it on request at any time, past the timer and the 30-day pause; a visitor who already answered lands on the last step. Every opening keeps the same record id, so answers update one row. Interested visitors are offered a 30-minute meeting at `bookingUrl` (Cal.com); the only other line is that Marqoom is open source and non-profit. Keep this copy plain: no "free", no reassurance that we are not selling, no feature pitch. Others get a thank-you and the terminology. `?survey` opens it at once for checking.
- `app/api/visitors/route.ts` stores each answer as it is given in Cloudflare D1 (`DB` binding in `wrangler.jsonc`, schema in `migrations/`), validating every code against `lib/visitor-survey.ts`. No names, emails or IP addresses are stored. Locally, `npx wrangler d1 migrations apply marqoom --local` lets `npm start` write to a local database.
- `app/api/search/route.ts` uses English and Arabic tokenizers. Do not index obsolete summaries alongside the current specification.
- `next.config.mjs` redirects the old vocabulary URLs. Preserve those redirects.

# In another terminal:
